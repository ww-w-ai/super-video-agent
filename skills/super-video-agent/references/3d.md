# 3D — WebGL films

Contents: When to use it · Install three.js · The cast stage · Characters and props from GLB
files · The capture path · Determinism rules · Speed · Text always in the 2D overlay · Craft that
worked · Prompting it

## When to use it

Reach for 3D when the picture needs real depth, physical light, or a camera flight through
space that 2D canvas cannot fake — a game-like flythrough, product/object turntables, a world
the camera moves through rather than cuts between. Most films should stay 2D; 3D costs far more
render time (see "Speed") and is worth it only when the depth itself is the point.

## Install three.js

Not bundled with this skill. Install it once, into the reel or next to the skill:

```
npm install three --prefix <reel-dir>
```

`new-reel.mjs <dir> --3d` then copies `three.module.js`, `three.core.js` and the whole
`examples/jsm/` tree (as `assets/vendor/addons/`, keeping `loaders/` and `utils/` side by side for
their relative imports) into the reel. It looks for the package in `$SVA_THREE_DIR`,
`<dir>/node_modules/three`, then `<skill>/node_modules/three`, and prints the steps when it finds
none. Installed later? `new-reel.mjs <dir> --vendor` copies the files and touches nothing else.
Record the installed version and its MIT license in `FILM.md`.

The scaffold's import map is live: `"three"` → `assets/vendor/three.module.js`, `"three/addons/"` →
`assets/vendor/addons/` (addons import the bare name `three`, which only an import map resolves).
The scene loads three.js and its `ADDONS` list (`loaders/GLTFLoader.js`, `utils/SkeletonUtils.js`;
trim it to what the film uses) with dynamic imports, so a missing file rejects `ready` with one
message naming the files and the install step instead of a bare module-resolution error.

## The cast stage

A 3D film with its own characters needs a cast stage between the voice and the film. It builds
the models, checks them in the film's own renderer and gets the owner's approval of a lineup
before any shot is built. It hands the film two things: the GLB files and a contract table.

0. **Look in the asset library first.** Characters, props and sets from earlier films are
   catalogued there: `assets.mjs search --role character <words>` lists rigged state, clip names
   and licence, and `assets.mjs model <id> <reel-dir>` copies one into `assets/models/<id>/`
   (`references/pipeline.md` "Asset library"). Build only what is missing.
1. **Build** every character, prop and set with one generator script ("Characters and props from
   GLB files" below).
2. **Preview** them in Blender stills for shape and pose.
3. **Try them in three.js.** `new-reel.mjs <dir> --testbed` scaffolds a `window.__reel` page that
   loads the `.glb` files under `assets/models/` (also those in `<id>/` folders) and shows a lineup and a turntable, one view per second, with a
   level-hold helper (`holdLevel`) and a face toggle. Add the scenery and props, render views
   with `still.mjs <dir> --at <t>`, and tile them with `still.mjs --sheet <out.png> <a.png> <b.png> …`.
4. **Judge colour in the three.js stills**, not in Blender's EEVEE previews, which read paler in the
   Standard view. Painted blush and decal edges read darker and sharper in three.js; soften their
   edge and alpha.
5. **Show the owner a lineup still** and fix the generator until it is approved.
6. **Write the contract table** below. The film page reads it instead of guessing.

**The contract table.** `scripts/glb-info.mjs <file.glb>` prints what the loader sees: roots,
clips with durations, node names with dots already stripped, morph targets and triangle counts.
Start the table from its output.

| Entry | What to record |
|---|---|
| Node names | every node the page looks up (characters, faces, sockets, props, sub-nodes), as GLTFLoader names them |
| Faces | the face nodes of each character; the page shows exactly one |
| Sockets | named empties where props attach (hands, a leash ring) |
| Clips | name, length in seconds, what each is for |
| Seat and surface heights | each seat's top and each table or counter top, above its base |
| Holds | per clip: the prop, its socket or sockets, offset and rotation in the character's frame, level or parented |
| Sub-nodes | parts the page animates (a door leaf, clock hands, a stream), with pivot and axis |
| Morph targets | name, index, and what 0 and 1 mean |
| Scale factors | per set, and per prop placement where it differs |
| Toggled nodes | accessories hidden by default and the scenes that show them |

**Character check list** (any style). Check each character in the three.js lineup:

- The species reads from its distinguishing features: ear shape and place, head proportions.
- Face features sit inside the 3D parts they belong to (a mouth on the muzzle, not beside it).
- A species gets no features it lacks.
- A bent flat part (a folded ear, a brim) stays one continuous surface, and its inner face follows
  the bend.
- Limbs show no joints unless the style is jointed.
- The owner has seen a lineup still before the film.

`examples/3d-round-plush-cast/` is one worked cast in one style (round, big-headed plush animals):
generator, testbed and a filled contract. It is an example, not a default; another film may need
a different build.

## Characters and props from GLB files

A film can load models instead of building everything from primitives in the page: characters
you model yourself in Blender, and free props, scenery and lighting from asset libraries.

**Modelling in Blender by script.** Blender runs headless: `blender --background --python make.py`
builds meshes, an armature and actions, exports a GLB (`bpy.ops.export_scene.gltf`, format
`GLB`, `export_animation_mode="ACTIONS"`) and renders EEVEE preview stills — confirmed on an
Apple M2 with Blender 5.2, about a minute per character including previews. If Blender is not
installed, install it (`brew install --cask blender` on macOS, or blender.org). Things that
cost a build to learn:

- **Look at the preview stills before the film uses a model.** Shape, proportion and whether a
  pose reads are judgments only a picture answers; render front and three-quarter stills of each
  action and fix the script until they read. Judge colour later, in three.js ("The cast stage").
- **Weight rigid parts to one bone each** (a vertex group per part, weight 1.0) when a character
  is assembled from separate primitives. Automatic weights fail on disconnected pieces. Rigid
  pieces cannot fold, so they never tear into flaps.
- **A skin-blended (welded) body has its own traps.** A colour border inside a blend band tears
  into flaps, so put colour borders on piece borders. A blended shoulder stretches the torso side
  in raised poses and would need corrective shapes. Decimating a remesh makes slivers; set the
  triangle budget with the remesh voxel size instead. Metaballs shrank some parts and left others
  floating.
- **Author bone rotations about world axes**, converted into the bone's rest frame
  (`rest⁻¹ · R · rest`). A bone's local axes depend on its direction and roll; keying a guessed
  local axis sent a waving arm behind the head.
- **Key a vertical root bone's offsets on its local Y.** A bone pointing up has local Y = world up
  and local Z = world −Y. Offsets keyed on local Z slid seated characters backward instead of
  lowering them.
- **Split a head turn, nod or tilt between the neck and head bones** (about 40/60), so it reads
  soft.
- **Check every gesture pose against the head** from the film's own camera angles. Big gestures
  come from the shoulder with a modest elbow. A raised arm can hide behind a big head at
  three-quarter view; stage waves toward the camera.
- **Name nodes with underscores.** GLTFLoader strips dots from node names (`hand.R` becomes
  `handR`). Sockets, faces, props and sub-nodes named with underscores keep their names.
- **One action per clip, `use_fake_user = True`**, then export with animation mode `ACTIONS`;
  every action becomes a named clip in the GLB.
- Build one parameterized script (species, colours, clothes) when a film needs several
  characters: they share proportions and one skeleton, so every clip works on all of them.

**Props, sets and cloth.** Build them in the same generator, sized to the cast:

- **Size hand props to the character's hands**, not to real size, and bake the scale into the
  meshes in the generator.
- **Scale sets to the characters** (a door fits the character), with one factor per set, not to
  real-world size. Record the factor in the contract.
- **A seated character's origin sits on the seat top**, and the sit clips drop the root by a fixed
  amount so the body rests there. Record each seat's top height.
- **Moving sub-parts** (a door leaf, a hanging board, clock hands, a bell) are child nodes with
  their origin at the pivot. Model a stream or rope one unit long along its axis, so its scale
  equals its length.
- **An accessory worn only in some scenes** is a separate node, hidden by default and switched per
  scene.
- **Cloth over a posed character** (a blanket): drape the sheet over the character's real posed
  vertices in the generator, and store the second state as a morph target driven from `t`. Between
  the draped poses the body can poke through ("Covers and soft bodies: nothing pokes through").

**Free assets.** Prefer CC0 (Kenney, Quaternius, Poly Haven HDRIs); CC-BY is fine with its
credit line in the film's credits; never NC. Verify the licence on the source page, record each
asset's source URL and licence in `FILM.md`, and keep the look consistent with your own models —
mixed styles (blocky props next to smooth characters) read as a collage; render a test still
before committing to a set. Restyle downloaded scenery toward the film's palette in the page
(material changes after loading), drop pack items that stay off-style, and compare an as-shipped
still with a restyled one.

**Sky, light and metal.** An HDRI can light the scene without being its backdrop; judge it as a
backdrop separately. Grey clouds read gloomy; a painted gradient sky behind the scene can replace
it. Metal needs an environment to reflect: metalness 1 with a weak environment reads as black
plastic, so raise `envMapIntensity` and set roughness around 0.2.

**Loading and animating.** `new GLTFLoader().loadAsync(url)` inside the `ready` chain, before
the world is built. Several copies of a rigged model: `SkeletonUtils.clone(gltf.scene)`, never
`.clone()` (that shares one skeleton, so every copy moves together). One `AnimationMixer` per
copy; in `seek(t)` call `mixer.setTime(localT)` — it zeroes the mixer's time and samples every
active clip at `localT`, so the sampled pose is a pure function of `t` and the determinism probe
passes. Never `mixer.update(delta)`, which carries time across frames. The mixer writes a bone
only when its sampled value differs from the previous call's (`PropertyMixer.apply` compares its
two accumulation buffers): a bone you moved after the mixer (head turn, IK, a hand placed on a
prop) keeps your value whenever the clip's value did not change, and a seek to another time then
starts from your value instead of the clip's, so the result depends on the order of seeks. Right
after `setTime`, copy each bone you will change (its quaternion or position) before you change it;
at the start of the next seek, write those copies back, then call `setTime` again. Cross-fades between clips: set each action's weight from `t`, not from `fadeIn()`.
Weights are relative, not absolute: the mixer normalises the weights of the actions active on a
bone (a running weighted average), so 0.5/0.5 and 1/1 blend the same way; only when the weights
sum to less than 1 does the remainder come from the bone's original (bind) value.

Two ways to hold a prop. A **level hold** places the prop at the socket's world position (the
midpoint of two sockets for a two-hand prop), rotates it with the character's root, adds the
contract's offset, and is recomputed every seek after `mixer.setTime`. **Parenting** the prop to
the hand socket makes it tilt with the paw, which is what a sip needs.

**Faces that change.** Paint each expression as a texture on a thin shell just over the face and
switch shells by visibility from `t`. It works for any drawn-face style, and it also covers a
downloaded model whose face is baked into its texture. Build each shell from the source surface:
copy the faces in front, lift them a few millimetres, drop the primitive's own UV map (otherwise
glTF uses the sphere UVs and shows one giant eye) and project flat front UVs. Use alpha BLEND for
soft painted edges, ordered after the base (see "Covers and soft bodies"). Put the same decal on every 3D part the features sit on (a muzzle, cheek
puffs), so the mouth lands on them. Outfits work the same way: a decal shell on the body front
keeps a clean edge at any mesh density.

**Downloaded models without a skeleton.** Models from generator galleries are often one static
mesh of 0.5–2M triangles, meshopt-compressed (register `MeshoptDecoder` from
`three/examples/jsm/libs/meshopt_decoder.module.js` on the loader). Weld vertices before you
decimate (in Blender), or the UV seams open into gaps; about 150k triangles rendered about 1.6×
faster than the original with no visible loss. What moves them, from safest to riskiest:

- whole-body motion from `t`: hop, squash-and-stretch with volume kept (y × s, x and z × 1/√s),
  lean, turn;
- a vertex deformation weighted by height, feet planted: sway, nod, breathe, small waves of a
  limb that stands clear of the body. Put the same bend in a `customDepthMaterial`, or the
  shadows stay unbent;
- cutting a part off in Blender: clean only where a narrow joint gives a closed cut (a neck), and
  even a clean cut shows its join once the head moves; a cut through a limb fused to the body
  leaves a visible flat face as soon as it rotates.

Walking, raised arms and swapped expressions need a skeleton and a separate face; choose models
that have them, or add them. Use static downloads for background or ensemble toy beats and rigged
characters for anyone who acts. Check each downloaded model's licence on its platform: the terms
for your own generations and for other users' uploads often differ.

**Soft bodies** (food, jelly, cushions, anything that wobbles). Drive every touching mesh with
one deformation field of rest position and `t`, not one motion per mesh: touching pieces then
move together and no gap can open between them. Rigid pieces with their own phase open gaps at
the seams. Recompute normals from the field so shading follows, and attach contact props (a fork
tip) to the same field. A damped ring `(1 − e^(−u/attack)) · e^(−u/τ) · sin(2πfu)` after the
touch, with a small delay per height, reads as a real wobble. What else it needs:

- **Glue the base.** No motion at the contact height, so nothing slides on or sinks into what it
  sits on.
- **Let the lag grow in** over the first period. A full lag from the touch makes the top move
  toward the tool at first.
- **Tilt each slice by the sway gradient.** Without it the lean reads as a shear.
- **Keep the field on the CPU.** One function then serves the mesh, its shadow and the contact
  prop. A vertex shader would need a copy in the depth material and analytic normals.
- **Measure, do not judge stills.** Track the displacement in pixels per frame against the rest
  pose under the same camera, not against frame 0 (a camera move shows up as fake drift).

**Covers and soft bodies: nothing pokes through.** When a cover moves (a quilt sliding, a sleeper
turning under it) or a soft body wobbles, parts that belong under or behind it can show through.
The z-buffer already orders opaque pixels, so draw order is not the fix. There are two causes:

1. **The geometry really interpenetrates.** A drape baked once for one pose does not follow the
   next pose, and a prop attached to a soft body (syrup, a fork, toppings) that is not moved by the
   same deformation field sinks in or floats off.
2. **Alpha-BLEND materials** (face and outfit decals, a glaze) write no depth and are sorted per
   object, so they can draw in the wrong order.

What fixes each:

- **Cover mask (the main fix).** Tag the parts that must stay under the cover in that shot, and
  leave untagged only the parts that come out in it. Decide per shot from the pose, not per body
  part: arms tucked under a quilt are tagged, arms resting on top of it are not. Every seek, after posing,
  render the cover's footprint on its base plane into a mask (or build its outline as a 2D
  polygon), and in the tagged parts' fragment shader (`onBeforeCompile`) discard fragments inside
  it. Outside the footprint they draw normally, so a leg leaving the cover appears, cut at the
  cover's edge. It is computed from the posed scene, so it stays a pure function of `t`. Clone the
  materials you patch, or every copy of the model loses those fragments. Shadows use the depth
  material, not the patched one; patch a `customDepthMaterial` too if a hidden part's shadow shows.
- **Its limit: a tagged part that rises under the cover** needs the cover to bulge, and the mask
  only hides it. There, re-drape the cover per seek instead: push its vertices to stay at least a
  small clearance above the posed body vertices (the generator's drape, run at seek time). A part
  resting on top of the cover (paws over a blanket) is untagged and also needs the re-drape where
  the cover would slide over it.
- **Soft bodies:** every attached prop gets the same deformation function as the body it sits on.
- **Transparent decals:** give each decal an explicit `renderOrder` after its base and
  `depthWrite = false`. When the edge can be hard, `alphaTest` instead of BLEND writes depth and
  needs no ordering.
- **Check it:** `scripts/overlap.mjs <reel> [--step <frames>] [--out <json>]` seeks the page frame
  by frame and calls the optional hook `window.__reel.overlap(t)`, which returns
  `[{pair: "<cover>/<part>", count: <vertices on the wrong side>}]` for that frame. It prints the
  spans where a count is above 0 per pair and writes them as JSON; it reports and never fails the
  reel. Count only parts that must stay under or behind, and leave out vertices the mask hides;
  a part that is allowed out would be reported on every frame. Without the hook it says so.

`examples/3d-round-plush-cast/cover/cover-mask.js` is one worked version (a quilt over a sleeper,
with the hook in that example's testbed).

**Blinks: drive them from a fixed list, expose the eye state.** A character that blinks too fast
or too often reads as nervous or glitchy, and a screenshot cannot show it. Drive blinks from a
fixed list of start times or a fixed period (never `Math.random` or a timer; the seek must stay
a pure function of `t`). Human-range values are a starting point: each about 100–400 ms from first
closing to fully open, about 2–10 s apart. Give the page the optional hook
`window.__reel.blink(t)` → `[{character: "<name>", closed: 0..1}]`: the eyelid morph influence
(`eyeBlinkLeft`, `eyesClosed`) or the lid bone's closing value, 0 open, 1 shut, one entry per
character (or per eye, `"<name>.L"`), read from the state the seek just set. `scripts/blink-check.mjs`
calls it after each seek and reports each character's blink count, intervals and closing times,
flagging blinks under ~100 ms, starts under 1.5 s apart and three blinks inside 1 s; it reads the
code for the same first (`references/qa.md`). For a baked clip, `--glb <file>` reads the
blink morph keyframes with no page. Without the hook it says so.

**A risky shot first.** When one shot carries the film (the hook), build it alone in a small
test reel with a stub `voice/timings.json`, render it and show it. Once it is approved, retime
it to its slot by changing its time constants and splice that render into the film's picture
instead of rebuilding it inside the film. `render.mjs --insert <clip.mp4>@<start-sec>` replaces
the picture's frames from that time with the clip, re-stamps them onto the 1/fps grid and checks
the inserted span by framemd5. A plain `-c copy` concat shifts the later timestamps, and the dub
step then counts the wrong number of frames. So that stills and previews show the shot too, the
page draws JPEG stills of the approved clip for that span (`--insert-stills <dir>` writes them);
the final picture swaps in the clip itself.

## The capture path — and why `readPixels`, never `drawImage`

`scripts/lib/browser.mjs` captures the reel by calling `canvas.toDataURL()` on the page's single
`<canvas>` (`references/pipeline.md`, "Page contract" — the renderer needs exactly the pixels the
engine drew). A 3D scene draws into a second, detached canvas (`document.createElement("canvas")`,
never added to the DOM, so the HTML keeps its one `<canvas>` tag — `verify.mjs`'s static scan
requires that) and must be copied onto the 2D stage canvas every frame.

**Never `ctx.drawImage(glCanvas, ...)`.** Copying a live WebGL canvas that way varies by up to one
colour level between two draws of the identical frame — confirmed by build: `verify.mjs`'s
determinism probe (seeks the same times in-order and shuffled, hashes every frame) failed at
20–300 scattered pixels. The GL buffer itself was identical; the canvas-to-canvas copy was not.

Instead: `gl.readPixels()` the WebGL framebuffer into a `Uint8Array`, write it into an
`ImageData` with `ctx.putImageData()`. That copy is exact, and the determinism probe passes.
Scaling that result up to the full frame with `ctx.drawImage()` afterward is safe — the source is
now a plain 2D canvas backed by `ImageData`, not a live WebGL one, so there is no double-buffering
non-determinism left to copy. The scaffold's `copyToStage()` in `reel-3d.html` does exactly this.

## Determinism rules

Same as every reel (`references/pipeline.md`, "Page contract"), 3D adds one more place they bite:

- **The camera is a pure function of `t`.** Build it with `Reel.monotoneTrack(keys)` through fixed
  keyframes — never integrate velocity frame to frame, never read a live clock. `seek(t)` must
  produce the same camera position whether it is the first seek or the hundredth, in any order.
  The track is a monotone cubic: between two keys it never leaves their range. A Catmull-Rom
  spline overshoots there — a camera diving to a low key went under the ground.
- **The first seek draws what every later seek draws.** A cold page (verify.mjs's first probe)
  differed from a warm one in three ways; the scaffold fixes each:
  - Images resolve after `img.decode()`, not on `onload` (`loadImage`).
  - three.js computes bounding spheres lazily on the first frame drawn — a skinned mesh's from that
    frame's pose, an instanced mesh's from that frame's instances — and sorts draw order by them.
    `stabilizeScene()` computes them all once after the build, from the bind pose and the full
    instance sets. Call it again after adding anything later.
  - Draw-order ties fall back to object ids, which follow async GLB load order.
    `stabilizeScene()` breaks ties by each object's name path, then traversal order — give loaded
    roots stable names.
  - A skinned mesh culled with bounds from its first pose drew differently on a first seek:
    skinned meshes get `frustumCulled = false`.
- **No carried physics state.** Object rotation, position, anything animated is computed directly
  from `t` (e.g. `mesh.rotation.y = t * 0.35`), not accumulated across frames.
- **Randomness is keyed and drawn once.** Fixed scene elements (a starfield, scattered debris) get
  their positions from `Reel.rng(key)` at world-build time, not `Math.random()` per frame. If a
  visual needs to look random *and* vary with time, bucket time first (`Math.floor(t * hz)`) and
  key the RNG on that bucket, the same pattern `boil()` uses in 2D.
- **Blur and glow go over an opaque copy of the frame.** Draw the opaque frame first, then the
  blur or glow on top. A blurred draw's soft transparent edges keep part of the previous frame;
  that made `verify.mjs` fail at most probe times, and after the change it failed at none.
- `verify.mjs`'s static scan bans `Math.random`, `Date`, `performance.now`,
  `requestAnimationFrame` and timers in the SCENE block regardless of 2D or 3D.

## Speed

Headless Chromium has no GPU: WebGL2 falls back to SwiftShader, a CPU implementation. Measured on
the reference film: **0.3–1.2 s per frame at 810×1440** (0.75 render scale on a 1080×1920 frame).
A 40 s film at 30 fps (1,200 frames) took **about 20 minutes to render with 4 workers**.

- **Render scale 0.75 by default.** Render the 3D scene at `WIDTH * 0.75 × HEIGHT * 0.75`, then
  upscale the copied frame to full size with `ctx.drawImage()` (safe — see above, the source is a
  2D canvas). The 2D overlay (captions, titles) always draws at full resolution on top, so text
  stays sharp even though the picture underneath is upscaled.
- **Skip the 3D scene where it is not on screen.** Set `SCENE_WINDOWS` to the `[{start, end}]`
  spans that show it; `seek(t)` draws `draw2D(t)` instead of `render3D` + `copyToStage` elsewhere.
- **Run long 3D renders in the background.** A 40+ second 3D film is a 15–30 minute job; do not
  block the session on it.
- **Order: picture first, then dub each language.** Render the picture once
  (`render.mjs --no-captions`) and lay each language's captions + voice over it with `dub.mjs`
  (`references/pipeline.md`, "Picture first and language versions") — re-rendering the whole 3D
  picture per language would multiply the 15–30 minute cost by the language count for no reason.
  `SKILL.md`'s flow step 1 already recommends picture-first "when the picture renders slowly
  (3D/WebGL drawn on CPU, heavy effects)" — for 3D this is not a suggestion, it is the default.

## Text always in the 2D overlay

Never draw captions, titles or any text the viewer must read inside the 3D scene (as a texture,
sprite or in-world plane) — it inherits the render scale's softness and the lighting/fog tinting
it. Draw all of it in the 2D overlay after `copyToStage()`, at full resolution, the same
`Reel.caption()` / `textBlock()` / safe-area helpers 2D films use.

## Craft that worked

From the reference build (a 40 s flight: phone → night city → undersea cable → data center → GPU
chip → phone):

- **One continuous camera flight, no cuts.** The camera never teleports; every place change
  happens while it is already flying into something that fills the frame.
- **Portals through a surface that fills the frame.** A glowing slot, a tunnel mouth, a light
  pulse, a vent, a chip lid — the next place opens from the frame centre as the old one is still
  visible at the edges, so the transition reads as travel, not a cut.
  A visual rhyme is worth building between places the flight revisits or echoes (the reference
  film's chip-die grid was built to echo the night-city grid from above).
- **Bloom via half-float render targets.** Render the scene into a `HalfFloatType` target, run a
  bright-pass + blur-down/blur-up chain on it, composite back over the scene — cheap relative to
  full ray-traced glow and reads as "game-like" instantly.
- **Game-like lighting.** A directional key light, a coloured rim/point light, fog for depth —
  not flat ambient-only lighting.

From builds with several characters in one 9:16 frame:

- **Do not line the characters up small.** Fly close to each in turn, then pull back for the
  group.
- **Check that the camera path never passes through a foreground character**, especially on
  swings between them.

## Prompting it

Say "like a video game" and name the engine and the camera move — that combination is what
produced the most striking 3D films (`references/community.md`). "A real-time 3D scene like a
video game, built with Three.js/WebGL — one continuous camera flight with no cuts, from A to B to
C" gives the model both the tool and the shape; it invents the rest.
